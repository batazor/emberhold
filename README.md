# Вылазка — прототип на Three.js

Реализация этапов 1–4 из [DESIGN.md](DESIGN.md) §8.

**Вылазка:** изометрический рендер под ортокамерой, генерация локации по сиду,
движение тапом, ночь и фонарь, провиант, рюкзак, бой, эвакуация со ставкой.

**Лагерь:** четыре здания, один слот стройки, лестница таймеров, ускорение солью,
жители, оффлайн-прогресс и сохранение. Петля замкнута: добыча из вылазки
зачисляется на склад и тратится на постройки, постройки меняют следующую вылазку.

**Кузница (§14):** пять слотов снаряжения, ковка и улучшение **без таймера**.
Это второй сток из §20.1: пока занят единственный слот стройки, экран возврата
предлагает не «ещё вылазку», а ковку. Замер `npm run play` даёт 5% → 40–55%
возвратов с доступной покупкой (§20.1.2); сравнение включается
переключателем `NOFORGE=1`.

**Замыкание петли:** экран возврата с начислением добычи анимацией и главной
кнопкой-тратой, телеметрия §9 и сводка по ней прямо в игре (кнопка «Данные»
в лагере).

## Команды

```bash
npm install
npm run dev        # http://localhost:5173
npm run check      # правила: src/**/*.rules.ts, без браузера
npm run arch       # границы: слои, headless, изоляция фич, ссылки на §
npm run verify     # золотой мастер петли: сдвинулась ли игра
npm run baseline   # перезаписать мастер намеренным изменением
npm run measure    # замер добычи и провалов по ярусам, 300 вылазок ботом
npm run play       # одна сессия из двадцати вылазок, отчёт для чтения
                   # NOFORGE=1 npm run play — та же сессия без Кузницы (§20.1.2)
npm run build      # typecheck + check + arch + verify + vite build
npm run typecheck
```

## Структура

```
src/
  core/      rng (mulberry32), loop (фиксированный таймстеп), clock (монотонное время)
  sim/       config, types, grid, pathfinding, generate, enemies, raid,
             resources, camp, heroes, gear (снаряжение §14), save, session
  render/    scene (камера, свет, ночь), raidView, campView, palette
  ui/        hud (вылазка), campHud (лагерь), rosterPanel — DOM поверх канваса
  **/*.rules.ts  проверки лежат рядом с тем, что проверяют
scripts/
  arch.ts        границы, которые раньше приходилось помнить в ревью
  baseline.ts    золотой мастер петли
  measure.ts     калибровка ярусов ботом
  play.ts        печать одной сессии
```

**Главное архитектурное правило: `sim/` не импортирует three.** Симуляция —
чистые данные и функции, её можно гонять в тестах, на сервере и в воркере.
Рендер читает состояние, но никогда его не меняет. Это же условие делает
возможной серверную валидацию из §6 без переписывания игры.

Второе правило: симуляция идёт фиксированным шагом 1/60 с, отрисовка —
с частотой экрана и интерполяцией между тиками (`core/loop.ts`). Лагерь при этом
рисуется на 30 кадрах и замирает через 20 секунд без касаний (camp.html §3).

Благодаря первому правилу вся экономика проверяется в Node без браузера:
`npm run check` гоняет вылазку и лагерь как обычные функции.

## Как игра остаётся изменяемой вдвоём и втроём

Три проверки, которые держат стоимость правки независимой от размера игры.
Они не про то, что игра работает, — про то, что её можно менять параллельно.

**`npm run check` — правила рядом с кодом.** Каждый модуль приносит свой
`*.rules.ts` и никогда не правит общий файл проверок. Раньше проверки жили
в одном `scripts/check.ts`, и любые двое, добавляя своё, встречались в нём.

**`npm run arch` — границы вместо памяти.** Проверяются четыре правила:
слои знают только про то, что ниже; `sim/` и `core/` не тянут three и DOM;
фича видна другим только через свой `index.ts`; каждая ссылка `§N` в коде
существует в DESIGN.md. Последнее не теория: `§22` упоминался в четырёх
файлах, пока раздела не было.

**`npm run verify` — золотой мастер петли.** Восемь детерминированных сессий
по двадцать вылазок, сводка сравнивается с `baseline.json`. Правка боя,
сдвинувшая экономику лагеря, видна сразу и без чтения `camp.ts`. Если сдвиг
намеренный — `npm run baseline`, и diff мастера уезжает в тот же коммит,
объясняя ревью, что именно изменилось в игре.

## Чего ещё нет

События локации (§11.6), карты сборов (§19), звук (§18), Кузница, Лазарет и Плац
как здания, мировая карта и боты (§4). Модели и анимации — плейсхолдеры-примитивы,
как и предписано §6.1 для первых этапов.

Герои (этап 5) есть в симуляции целиком: три класса, умения, ротация, лечение
и тренировка (`sim/heroes.ts`, правила в `sim/heroes.rules.ts`). **Зданий под
ними пока нет:** таймеры лечения и тренировки висят на самом герое, а Лазарет
и Плац появятся вместе с остальными постройками. Атака, Защита и Сила хранятся
и показываются, но в бой не входят — бой ведётся ранами, и формулы урона §11.5
требуют замены модели боя целиком, а не половины.

Стоимость построек (§20.3) откалибрована замером `npm run measure`, но только
уровни 2–3 стоят на твёрдых данных: на ярусах 2–3 выживает 18% вылазок, и
добыча успешной вылазки там — выборка везучих коротких забегов. Уровни 4–6
пересчитываются тем же скриптом, как только бой перестанет быть главной
причиной провалов (см. §20.3.2).

## Отладочные органы управления

Ползунок «Ночь» в вылазке и кнопки «Ярус 0–3» в лагере — не игровые механики,
а инструмент проверки. В игре ярус выбирается на мировой карте, а время суток
задаётся локацией. `?tier=N` в адресе открывает игру сразу в вылазке нужного
яруса. Кнопка «Данные» показывает сводку телеметрии и выгружает сырые события
в буфер обмена.

## Что смотреть в телеметрии

Сводка снабжена ориентирами из документа, потому что цифра без ориентира —
повод для спора, а не решение:

- **Глубина выхода** — ответ на ключевой вопрос §9 «эвакуируются ли слишком
  рано». Ниже половины локации — риск не окупается.
- **Провалов** — §11.3 хочет 65% по провианту и 35% по бою.
- **Покупка была доступна** — §20.1 целится в 60–80% возвратов.
- **Возврат после таймера** — сравнивать с лестницей §20.2.
